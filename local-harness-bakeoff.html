Local Harness Bake-off

Four coding-agent harnesses drove the same local model through the same three-stage Space Invaders build. All four ended with a playable game. They differ enormously in how much of the model's context they burn to get there — and that decides the recommendation.

Recommendation: local-agent opencode as your default harness for local models. It has a lean fixed prompt (~7.5k tokens vs Claude Code's ~25–31k), it drives Qwen's tool calls reliably, its permission model auto-runs in headless mode, and it built the game cleanly in 4.8 minutes with zero runtime errors. Use Aider when the question is "how good is this model at writing code" rather than "how well does it drive an agent loop" — it is the fastest and cheapest by a wide margin (154 s, ~2.5k prompt overhead) but its edit-then-hand-back workflow means you are the test runner. Claude Code works now with the wrapper, and produced a good game, but it is the heaviest and slowest. Qwen Code produced the prettiest build but is even heavier than Claude Code out of the box and needed the most tuning to behave.

Updated after Jim's play-test and a feedback round (17 Aug). Hands-on play found what the "renders, no exceptions" probe could not: Claude Code's build had no invaders until Enter was pressed, Aider's formation went straight down, OpenCode's ship was oversized, and none of them restarted a wave (stage 4 hadn't been run). A second round fed each harness the bug reports verbatim plus stage 4, and pi (pi.dev, already installed) joined and ran the whole pipeline. Every harness fixed its reported bug in one short turn (21–65 s); the validator gained "observe" (is the formation present and moving sideways on load?) and "clear-level" (kill all invaders via page state, does a new wave appear?) checks that now catch all of the above. Details in the new sections below; the original report follows unchanged.

Revised recommendation

Two harnesses stand out for different reasons. Qwen Code (as tuned by the wrapper) produced the game Jim rated as the only truly playable one first time and the cleanest stage 4 — it thinks longest and self-checks (it ran node --check unprompted) — at the cost of being the slowest and heaviest. pi is the opposite pole: a 1.5k-token prompt, four built-in tools, four stages in the time others took for two, and the fastest, most precise debug turns of the set — but it never verifies its own output, so you are the test loop, and it shipped two logic bugs the others' longer deliberation avoided. OpenCode remains the balanced default; Aider is the efficient pair-programmer; Claude Code works but is the heaviest.

Honest caveat on the game-logic bugs: with one sampled run per harness at temperature 1, whether a given build has an off-by-one is mostly model dice, not harness quality. What the harness genuinely determines is prompt overhead, speed, how much of the window is left for thinking, whether it nudges the model to self-verify, and how well it drives fixes — and on those, the table above is the real comparison. Wrapper: local-agent pi is now available (private PI_CODING_AGENT_DIR with a models.json carrying the real context window). Note that the ollama launch pi probe upgraded pi 0.70 → 0.84 and added a qwen3.8:latest default to ~/.pi/agent/; the wrapper itself leaves those files alone.

What was wrong in the first place

Your original failure ("Claude's response exceeded the 32000 output token maximum") was a context-window problem wearing an output-limit costume. Claude Code's interactive prompt tokenizes to ~30,600 tokens for Qwen; Ollama was serving a 32,768-token window. That left ~2k tokens per turn, the model hit the ceiling every turn (truncated = 1 in the Ollama log, five turns in a row), Ollama reported stop_reason: max_tokens, and Claude Code relayed that as its own cap. Two other facts checked empirically: Ollama's Anthropic-compatible endpoint ignores budget_tokens, so thinking is on/off only (it stays on); and with the KV cache quantized to q8_0, an 81,920-token window fits 100% on the 4090 at ~68 tok/s (about 100 tok/s in practice thanks to speculative decoding), whereas 96k+ spills to CPU and halves throughput.

The wrapper

~/.local/bin/local-agent starts a private ollama serve on port 11435 (context 81,920, q8_0 KV cache, flash attention, 2 h keep-alive; the system Ollama on 11434 is untouched except that its resident models are unloaded to free VRAM), preloads the model, reports the GPU split, then launches the harness with the real context window wired in. claude-ollama is kept as an alias for local-agent claude.

local-agent opencode                     # OpenCode TUI (recommended)
local-agent aider                        # Aider pair-programmer
local-agent qwen                         # Qwen Code TUI (edits auto-approved, shell asks; Shift+Tab cycles)
local-agent claude --dangerously-skip-permissions
local-agent --model qwen3.6:27b opencode # any Ollama model
local-agent serve                        # just the tuned server, for anything else
local-agent ps | stop

# headless one-shots
local-agent opencode run "…"
local-agent qwen --approval-mode yolo -p "…"
local-agent aider --yes-always --message "…"
local-agent claude --dangerously-skip-permissions -p "…"

Tunables: --ctx, --kv, --port, --max-output, or the CLAUDE_OLLAMA_* env vars. Server log with live prompt sizes: ~/.cache/local-agent/server.log (grep 'new prompt').

Harness by harness

OpenCode recommended

Configured entirely through OPENCODE_CONFIG_CONTENT (provider = @ai-sdk/openai-compatible at the private server's /v1, with the real context/output limits so its compaction is right). Lean prompt, reliable tool calls, opencode run auto-executes edits and shell in headless mode. Fastest of the true agentic harnesses. One gotcha found: it blocks on a non-TTY stdin that never closes — use </dev/null in scripts.

Aider best for model evals

Talks to Ollama's native /api/chat; the wrapper generates model metadata (window/output) and settings (diff edit format, repo map, explicit num_ctx). Tiny prompt, text-based edits (no tool calling needed), git-native, shows the model's thinking. It cannot test its own work, so treat it as pair-programming: you run it, paste errors back. With --yes-always it will also run suggested commands such as xdg-open.

Claude Code heaviest

Works via ollama launch claude pointed at the private server, plus CLAUDE_CODE_AUTO_COMPACT_WINDOW=81920 and a 30-min API timeout. Solid results, and it self-verified with shell commands, but ~25–31k of every window goes to its own prompt and tool schemas, and by stage 3 the conversation was at 58k tokens. Fine for occasional use; not the harness that shows the model at its best.

Qwen Code heavy, tunable

Stock, its prompt is 33k (workflow, cron, artifact, computer-use, subagent and deferred-tool machinery), it defaults to an LLM approval classifier (extra local-model calls per tool use), and it assumes a 200k window. The wrapper gives it a private QWEN_HOME whose provider entry carries the real window and turns the extras off — prompt drops to ~16k and it auto-compacts correctly (observed: 50k → 25k mid-run). Best sprites of the four. Headless needs --approval-mode yolo.

Caveats

  • One model, one task, one run each — this is a functional shakedown, not a benchmark. Sampling at temperature 1 means a rerun would land differently in detail; the overhead numbers and the "does it work at all" verdicts are the stable parts.
  • Prompt overhead was measured for headless mode; interactive prompts are somewhat larger (Claude Code: 25k vs 31k). OpenCode's and Aider's TUIs were launched and reached their prompts under the wrapper but were not driven interactively.
  • Qwen Code's stage 1 timing is pre-tuning; the two failed stage attempts caused by the loop-detector mistake are excluded from its totals but noted above.
  • Codex CLI is wired into the wrapper (via ollama launch codex) but untested; it pairs naturally with your gpt-oss models rather than Qwen.

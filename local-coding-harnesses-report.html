Local Coding Harnesses

Five terminal coding agents, four models, two objectively-graded programming tasks, and one arcade game — measured end to end on one 24 GB GPU. Which harness, which model, and why the answer to each depends on the other.

Bottom line

For day-to-day local coding: pi with qwen3.8. pi carries the leanest prompt of any harness (~1.5k tokens vs 7.5k–31k), and qwen3.8 was the only local model that reliably closed the write-run-verify loop — it scored a perfect 70/70 on a TOML parser written from spec through pi. Keep opencode as the fallback for any other model or when you want guardrails. But the headline finding is a caveat: on hard, open-ended tasks the harness and the model interact — the same qwen3.8 that aced the task through pi produced nothing through the heavier harnesses, because it spent the whole turn planning instead of writing. Match the harness weight to the task, not to a leaderboard.

This is the sequel to the Space Invaders bake-off, which established the tooling (a tuned Ollama server, the local-agent wrapper, a headless-Chrome validator). That round showed all five harnesses can drive a local model, but graded on a game — subjective. This round grades on programs a script can score exactly, swaps in a cloud-hosted 116B model to strip out small-model noise, and pits qwen3.8 against gemma4:26b.

How it was measured

Two tasks, each graded by a hidden test suite the model never sees, using a reference implementation as oracle:

  • tomlq — a TOML-subset-to-JSON command-line tool, parser written from scratch (stdlib only; tomllib forbidden and detected). Graded against Python's own tomllib across 70 cases: values, escapes, multiline strings, all integer bases, dotted keys, arrays of tables, and 29 malformed inputs that must be rejected with the right exit code. Run in two phases: spec only, then with a visible test file handed over to iterate against.
  • jpatch — a JSON Patch (RFC 6902) applier with JSON Pointer, graded against the jsonpatch library across 67 cases including atomicity, test ops, and malformed patches. The visible test file is present from the start (test-first).

Both grade the compiled behaviour of the produced .py — exit codes and stdout — so a file that doesn't run scores zero, exactly as it would in real use. Sampling was pinned to each model's own recommended values on every request (temperature 1.0, top_p 0.95 for the Qwen models), verified on the wire.

The honest verdict on the two models

qwen3.8 is the better agentic coder here, but the gap is about discipline, not raw code quality. When qwen3.8 closed the loop it was excellent (70/70, 65–67/67). gemma4:26b's one complete attempt — JSON Patch through OpenCode — scored 55/67, which is respectable; its underlying patch logic isn't far off qwen's 66. gemma's problem is that it frequently doesn't finish the agentic contract: it prints code to the chat instead of invoking the write tool, or writes a library without the command-line entry point the task requires, or stops after one malformed tool call. qwen3.8 also wins a hardware point unrelated to intelligence — its KV cache is small enough to run at an 80k context on the 4090, while gemma4:26b must drop to ≤40k to stay on the GPU at all.

The finding that reframes everything: closing the loop

Why did qwen3.8 score 70/70 on TOML through pi but 0 through OpenCode and Qwen Code — the same model, same task, same hardware? The session logs are unambiguous. Through the heavier harnesses, qwen3.8 spent its entire headless turn reasoning in the text channel:

"Let me start by understanding the task. I need to write a single-file
 Python 3 program tomlq.py… Let me plan this out… The current working
 directory is… Let me think about the implementation carefully. ## …"

…and the turn ended before it ever emitted a write_file call. Seven minutes of planning, zero files. Through pi — whose prompt is a screwdriver, not a manual — it just wrote the parser.

The pattern across every cell points to an interaction, not a ranking:

  • Open-ended task + heavy harness prompt → the model plans instead of acting. "Write X and test it yourself first," wrapped in a 16k-token system-and-tools prompt full of workflow guidance, invites a thinking model to deliberate until the turn is gone.
  • Constrained task or a visible test file → the loop closes everywhere. JSON Patch (a test file sitting in the directory, a concrete "make this pass" target) succeeded through every harness for qwen3.8: 65, 66, 67.
  • A lean harness closes the loop even when the task is open-ended, because there's less prompt pulling the model toward ceremony.

So the earlier zeros for both models on TOML-through-heavy-harnesses are substantially a task-framing artifact, not pure capability. That cuts against a simple "pi is best" story just as much as it cut against "gemma is bad."

Prompt overhead — the fixed token cost before you type anything — is the clearest axis the harness controls. Measured on the wire against the real tokenizer:

~⅔ of it is 24 tool schemas — subagents, git worktrees, goals, monitors, MCP — most unrelated to editing one file.

Claude Code

25k

Heaviest. ~25k headless, ~31k interactive. On an 80k window that's a third gone before the first token.

Qwen Code is the instructive case. Proxying its first request shows ~6.6k tokens of system prompt (21 sections of engineering methodology) and ~14k tokens of tool schemas for an agent platform — agent, create_sub_session, enter_worktree, monitor, update_goal, send_message — when the coding core is seven tools. But that heavy system prompt is not pure waste: it's opinionated craft guidance (an explicit plan→implement→verify loop, anti-over-engineering rules), and on the open-ended Space Invaders build in round 0 it produced the best-judged game of the five. The overhead that hurts on a single graded file is the scaffolding that helps on a sprawling one.

Two engineering notes from the trenches

Sampling drifts unless you pin it

Left alone, the OpenAI-compatible path sends top_p=1.0 (not the model's 0.95) and Aider sends temperature 0 — greedy decoding, which Qwen explicitly warns against for a thinking model. The wrapper now reads each model's Modelfile parameters and pushes them into every harness explicitly; verified identical on the wire.

Ollama can't dial qwen3.8's reasoning

qwen3.8 defaults to maximum reasoning effort, and Ollama's renderer ignores the effort level — think: low produced the same ~56k characters of reasoning as max. Only bypassing Ollama with llama-server + a fixed Jinja template restored the control (and a token budget cap, which on JSON Patch changed the score by one point — 66 vs 65 — so it costs little quality).

Recommendations

  1. Default: local-agent pi with qwen3.8. Leanest prompt, fastest turns, and the model closed the loop reliably. Best for tight, well-specified, single-file work and for iterating against a test file.
  2. Give the model a target, not an essay prompt. The single biggest quality lever wasn't the harness or the model — it was task framing. A visible test file or a prescriptive spec closed the loop everywhere; "write X and test it yourself" let thinking models plan until the turn died. Hand over tests.
  3. Fallback: local-agent opencode. The most robust across models — it validated tool arguments and produced complete files where pi let a good model ship a broken one. Use it for any model other than qwen3.8, or when you want guardrails.
  4. Reach for Qwen Code for big, open-ended builds (a new app, a game), where its workflow scaffolding earns its 16k — and where the 4090 can spare it. Not for single graded files.
  5. Model: qwen3.8 over gemma4:26b for agentic coding on this hardware — better loop-closing and it fits an 80k context. gemma's code is decent when it finishes; it just often doesn't.
  6. Aider stays the sharpest instrument for "how well does this model write code," distinct from "how well does it drive an agent." Claude Code works but is the heaviest; save it for when you specifically want its features.

Caveats

  • Each cell is a single sampled run at temperature 1. The objective scores are exact, but a given cell would land differently on a re-run; the stable signals are the large gaps (70 vs 0, loop-closes vs doesn't) and the prompt-overhead and speed numbers, not one-point differences.
  • Two tasks, both parsing/transforming structured text — a real but narrow slice of coding. They reward correctness and edge-case discipline; they say nothing about UI work, large-codebase navigation, or long multi-file refactors.
  • The gemma4 VRAM-starvation episode is a reminder that local benchmarking is as much about the host as the model — always confirm ollama ps shows 100% GPU before trusting a number.
  • Gemini CLI was considered for gemma and excluded as non-comparable: its only local path runs a 1B on-device Gemma, and it has no OpenAI/Ollama provider to reach gemma4:26b. The fair equivalent — gemma4 through Qwen Code, a Gemini-CLI fork — is in the table above.
